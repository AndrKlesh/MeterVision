# Техническое задание на разработку клиент-серверного приложения для автоматизированной передачи показаний приборов учета

**Название проекта:** MeterVision
**Тип проекта:** учебный (командный проект студентов)
**Состав команды:** 7 человек
**Стек:** Flutter, ASP.NET Core, PostgreSQL, EasyOCR, OpenCV

## 1. Общие сведения

### 1.1. Наименование
Кроссплатформенное мобильное приложение и серверная инфраструктура для передачи показаний приборов учета по фотографии.

### 1.2. Цель проекта
Создать систему, позволяющую пользователю передавать показания приборов учета (счетчиков) без ручного ввода. Пользователь фотографирует счетчик — система автоматически распознаёт показания и серийный номер, показывает результат пользователю для подтверждения/редактирования и сохраняет подтверждённые данные в БД.

### 1.3. Задачи проекта
- Разработать мобильное приложение на Flutter (Android + iOS).
- Разработать backend на ASP.NET Core с REST API.
- Разработать модуль распознавания на Python (EasyOCR + OpenCV).
- Спроектировать и реализовать схему БД PostgreSQL.
- Спроектировать контракты API.
- Обеспечить интеграцию всех компонентов.
- Провести тестирование и подготовить документацию.

### 1.4. Границы проекта

**Входит в MVP:**
- Аутентификация по логину/паролю.
- Съёмка счётчика.
- Отправка фото.
- Распознавание показаний и серийного номера.
- Подтверждение от пользователя.
- Сохранение в показаний в БД.

**Не входит в MVP:**
- Push-уведомления.
- Offline-режим.
- Регистрация по Email/SMS.
- Восстановление пароля.
- История показаний.

## 4. Архитектура системы

### 4.1. Компоненты

1. **Мобильное приложение (Flutter)** — клиент для Android/iOS.
2. **Backend (ASP.NET Core)** — REST API, бизнес-логика, оркестрация.
3. **Сервис распознавания (Python)** — приём изображения, обработка OpenCV, распознавание EasyOCR.
4. **БД (PostgreSQL)** — хранение данных.
5. **Файловое хранилище** — для оригиналов фотографий.

### 4.2. Схема взаимодействия
```
[Flutter App]
    │ HTTP (JWT)
    ▼
[ASP.NET Core API] ──► [PostgreSQL]
    │
    │ HTTP (внутренний)
    ▼
[Python CV Service (EasyOCR + OpenCV)]
```
### 4.3. Сценарий основного потока

1. Пользователь входит в приложение (логин/пароль).
2. Делает фото счётчика.
3. Приложение отправляет фото на backend.
4. Backend передаёт фото в CV-сервис.
5. CV-сервис распознаёт показания и серийный номер, возвращает результат с оценкой уверенности.
6. Backend сохраняет оригинал фото в файловом хранилище и возвращает распознанные данные в приложение.
7. Приложение сохраняет черновик записи (фото + распознанные значения + признак «ожидает подтверждения») **локально на устройстве**.
8. Приложение показывает пользователю распознанные значения.
9. Пользователь подтверждает или редактирует значения.
10. Приложение отправляет подтверждённые данные (значение, серийный номер, ссылку на фото) на backend.
11. Backend сохраняет запись со статусом «подтверждено» в БД.
12. Приложение удаляет локальный черновик после успешного сохранения на сервере.

## 5. Функциональные требования

### 5.1. Мобильное приложение (Flutter)

#### 5.1.1. Аутентификация

- При запуске отображается экран входа (логин + пароль).
- Валидация полей на клиенте (непустые, минимальная длина).
- При успешном входе приложение получает токен авторизации и сохраняет его в защищённом хранилище устройства.
- Токен автоматически прикрепляется ко всем защищённым запросам.
- При получении ответа «не авторизован» — автоматический возврат на экран входа.
- Реализован выход из аккаунта с очисткой сохранённого токена.
- Отображение понятных пользователю ошибок авторизации (неверный логин/пароль, нет сети, сервер недоступен).

#### 5.1.2. Съёмка счётчика

- Экран камеры: видоискатель, кнопка съёмки, переключение камеры, вспышка.
- Запрос разрешения на доступ к камере (runtime permissions).
- Предпросмотр снимка с возможностью пересъёмки.
- Базовая валидация изображения перед отправкой (не пустое, размер и формат в допустимых пределах).
- Выбор фото из галереи.

#### 5.1.3. Отправка фото и получение результата

- Отправка фото на backend.
- Индикатор процесса обработки.
- Обработка ошибок: таймаут, ошибка сети, ошибка распознавания, ошибка сервера.

#### 5.1.4. Подтверждение и редактирование

- Экран подтверждения отображает:
  - фото счётчика;
  - распознанное значение показаний (редактируемое поле);
  - распознанный серийный номер (редактируемое поле);
  - уровень уверенности распознавания (по каждому полю или общий).
- Если уверенность распознавания ниже порога — визуальное предупреждение пользователю.
- Кнопка «Подтвердить» — отправка подтверждённых данных на backend.
- Кнопка «Отменить» — возврат к экрану съёмки без сохранения.
- Валидация перед отправкой: значение числовое, поля не пустые.

#### 5.1.5. История показаний

- Список переданных показаний с датой, значением, серийным номером.
- Детальный просмотр записи.

### 5.2. Серверная часть (ASP.NET Core)

#### 5.2.1. API аутентификации

- API должно обеспечивать вход пользователя по логину/паролю и выдачу токена авторизации.
- (Опционально) API выхода из аккаунта.
- Пароли хранятся только в виде криптографически стойкого хеша.
- Ограничение количества неуспешных попыток входа (rate limiting).

#### 5.2.2. API распознавания

- API должно принимать фотографию, инициировать распознавание через CV-сервис, сохранять черновик записи и возвращать распознанные данные и идентификатор записи.
- Проверка размера и типа загружаемого файла.
- Сохранение оригинала фото в хранилище; в БД хранится ссылка/путь.
- Корректная обработка ошибок CV-сервиса (недоступность, ошибка распознавания) с возвратом осмысленного ответа клиенту.

#### 5.2.3. API подтверждения и сохранения

- API должно принимать подтверждённые пользователем данные и сохранять их со статусом «подтверждено».
- Проверка принадлежности записи текущему пользователю.
- Валидация входных данных (числовое значение, формат серийного номера).
- API для получения списка показаний пользователя (с пагинацией).
- API для получения деталей одной записи.

#### 5.2.4. Общие требования к API

- Версионирование API.
- Единый формат ответа об ошибке.
- Наличие авто-документации API (Swagger/OpenAPI).
- Структурированное логирование.
- CORS-политика, достаточная для мобильного клиента.

### 5.3. Сервис распознавания (Python + EasyOCR + OpenCV)

- Внутренний эндпоинт, принимающий изображение и возвращающий результат распознавания:
  - значение показаний;
  - серийный номер;
  - оценка уверенности по каждому полю;
  - (опционально) полный распознанный текст для отладки.
- Предобработка изображения средствами OpenCV.
- Распознавание через EasyOCR.
- Постобработка: отсев мусорных символов, проверка формата числа, нормализация разделителей.
- Возврат оценки уверенности для каждого поля.
- Корректная обработка «нераспознаваемых» изображений (возврат осмысленного ответа, а не ошибки сервера).

## 6. Требования к данным

Команда самостоятельно проектирует структуру БД, при этом система должна обеспечивать хранение и обработку следующих сущностей и их связей:

- **Пользователь** — учётная запись, под которой выполняется вход.
- **Прибор учёта** (опционально для MVP) — привязка показаний к конкретному счётчику пользователя.
- **Показание** — запись, содержащая:
  - ссылку на пользователя;
  - ссылку на фотографию;
  - распознанные значения (показания, серийный номер);
  - оценки уверенности распознавания;
  - подтверждённые пользователем значения;
  - статус записи (например, «ожидает подтверждения» / «подтверждено» / «отменено»);
  - временные метки создания и подтверждения.

Требования к данным:

- Обеспечение ссылочной целостности.
- Возможность быстрой выборки показаний пользователя с сортировкой по дате.
- Хранение черновиков и подтверждённых записей раздельно по статусу.
- Хранение оригиналов фотографий вне БД (в файловом хранилище), в БД — ссылка.

## 8. Требования к окружению и инфраструктуре

- **Backend:** .NET 10, ASP.NET Core Web API, EF Core, Npgsql.
- **CV-сервис:** Python 3.11+, EasyOCR, OpenCV.
- **БД:** PostgreSQL 15+.
- **Мобильное приложение:** Flutter 3.x, пакеты для работы с камерой, HTTP-клиентом, защищённым хранилищем.
- **CI/CD:** GitHub Actions — сборка backend, линтеры, запуск тестов.
- **VCS:** Git (GitHub), feature-branch workflow.


## 9. Требования к качеству и тестированию

- **Unit-тесты:** backend/mobile — ключевая бизнес-логика (аутентификация, подтверждение).
- **Widget-тесты** набор тестов на корректную работы UI.
- **Integration-тесты:** API ↔ БД, API ↔ CV-сервис.
- **Тесты CV:** набор эталонных фото счётчиков (≥ 20 шт.) с ожидаемыми значениями; метрика точности распознавания ≥ 85% на тестовом наборе.
- **Ручное тестирование:** чек-лист по основному и альтернативным сценариям (нет сети, отказ CV, неверный формат).

## 10. Критерии приёмки

1. Пользователь может войти по логину/паролю и получить токен авторизации.
2. Пользователь может сфотографировать счётчик и отправить фото на backend.
3. Backend вызывает CV-сервис и получает распознанные показания и серийный номер.
4. Приложение отображает распознанные значения и позволяет их отредактировать.
5. По подтверждению данные сохраняются в БД PostgreSQL.
6. Пользователь может просмотреть историю показаний.
7. Точность распознавания на тестовом наборе ≥ 85%.
8. API задокументировано в Swagger.
9. README содержит инструкцию по развёртыванию и запуску.
10. Спроектированы и зафиксированы: ER-диаграмма БД и OpenAPI-спецификация.
