# Предобработка изображения (OpenCV)

Модули: `pipeline/image_io.py`, `pipeline/preprocessing.py`, `pipeline/locator.py`.

Все числовые параметры ниже **стартовые значения**: подобраны по образцу и опыту с подобными задачами, их нужно подтвердить на датасете (см. [configuration.md](configuration.md#6-тестирование-и-оценка-качества)). Сначала подключается минимальный набор шагов (итерация 1), затем добавляются остальные только если метрики улучшаются.

## 1. Цели

| Проблема на эталонном образце | Что с ней делаем |
|---|---|
| Блики и отражения на стекле и крышке (на образце сильные блики) | Выравнивание контраста, маска пересвеченных пикселей, локальный inpainting в кропе |
| Повороты кадра, портретная съёмка с телефона | Учёт EXIF-ориентации |
| Огромные фото с камеры телефона | Уменьшение до рабочего размера, контроль времени |
| Много посторонних надписей и цифр | Поиск дисплея и распознавание значения только внутри него |
| Десятичная точка на дисплее (на образце крупная, но её потеря меняет значение в 100 раз) | Не применять операции, стирающие мелкие объекты (opening, сильное размытие) |

## 2. Этапы

| № | Этап | Модуль | Что делает | Стартовые параметры | Итерация |
|---|---|---|---|---|---|
| 1 | Декодирование | `image_io.decode_image` | `cv2.imdecode` из байтов, ориентация по EXIF, проверка размеров и числа пикселей до полного декодирования. Ошибка → `InvalidImageError` | `MAX_IMAGE_PIXELS=40_000_000` | 1 |
| 2 | Уменьшение | `image_io.downscale` | Длинная сторона до `MAX_SIDE_PX`, `INTER_AREA`. Запоминается коэффициент для перевода `bbox` назад в исходные координаты | `MAX_SIDE_PX=1600` | 1 |
| 3 | Выравнивание контраста | `Preprocessor.enhance` | Перевод в Lab, CLAHE по каналу L, обратно | `clipLimit=2.0`, сетка `8×8` | 1 |
| 4 | Маска бликов | `Preprocessor.enhance` | Пиксели с высокой яркостью и низкой насыщенностью (HSV) считаются бликом. Маска нужна поиску дисплея и inpainting | `V ≥ 240`, `S ≤ 40` | 2 |
| 5 | Поиск дисплея | `DisplayLocator.locate` | Контурный поиск прямоугольника (раздел 3) | см. ниже | 1 |
| 6 | Подготовка кропа | `Preprocessor.crop_variants` | Несколько вариантов кропа дисплея для распознавания (раздел 4) | см. ниже | 1 (вариант A), 2 (вариант B) |
| 7 | Устранение мелких бликов | `Preprocessor.crop_variants` | `cv2.inpaint` только для небольших пятен внутри кропа. Крупные пересветы не трогаются (всё равно не восстановить) | пятно ≤ 3% площади кропа | 2 |

Шумоподавление (`fastNlMeansDenoising`, билатеральный фильтр) в план не входит. Оно дорогое по времени, и мелкую точку легко потерять. Включается только если измерения покажут пользу.

## 3. Поиск дисплея (`DisplayLocator`)

Классический подход без обучения:

1. Серое изображение, лёгкое размытие по Гауссу.
2. Границы (`Canny`) или адаптивный порог, затем замыкание (`morphologyEx` с `MORPH_CLOSE`), чтобы замкнуть рамку дисплея.
3. `findContours`, аппроксимация в четырёхугольник, `minAreaRect`.
4. Фильтр кандидатов:

| Признак | Диапазон | Основание |
|---|---|---|
| Доля площади кадра | 2–40% | Образец: ≈ 25%. Диапазон взят с запасом на другое расстояние съёмки |
| Отношение сторон | 1,5–8 | Образец: ≈ 2. Диапазон взят с запасом |
| Прямоугольность (`площадь контура / площадь minAreaRect`) | ≥ 0,75 | Дисплей это почти идеальный прямоугольник |
| Контраст внутри (стандартное отклонение яркости) | выше порога | Внутри дисплея есть тёмные цифры на светлом фоне или наоборот |

5. Из прошедших кандидатов берётся лучший по произведению контраста и прямоугольности. Если кандидатов нет, возвращается `None`.

Если дисплей не найден, сервис не падает: значение ищется среди токенов полного кадра, поле получает флаг `fallback_region` и сниженную уверенность (см. [recognition.md](recognition.md#7-оценка-уверенности)).

Если классический поиск окажется нестабильным на датасете, запасной вариант: найти текстовые блоки детектором EasyOCR и выбрать числовой блок с наибольшей высотой символов. Это решение принимается по метрикам.

## 4. Варианты подготовки кропа

Дисплей образца точечный (графический) ЖК с тёмными цифрами на светлом фоне. Кроп готовится в нескольких вариантах, каждый распознаётся, а побеждает вариант с лучшим результатом (валидный формат числа, затем наибольшая уверенность). Варианты нужны из-за бликов и неравномерной засветки.

| Вариант | Подходит для | Операции |
|---|---|---|
| A. «Контраст» (итерация 1) | Нормальное освещение, хорошо контрастный текст | Серый, увеличение в 2 раза, CLAHE. Без бинаризации |
| B. «Адаптивный» (итерация 2) | Неравномерная засветка, блики | Адаптивный порог (`ADAPTIVE_THRESH_GAUSSIAN_C`) по увеличенному серому кропу |

## 5. Что не делается

| Не делается | Почему |
|---|---|
| Исправление перспективы (`warpPerspective`) | В первой версии пользователь снимает «в лоб» (приложение даёт рамку). Добавлять, если измерения покажут перекос |
| Нейросетевой детектор дисплея | Нет размеченных данных. Пересмотреть после сбора датасета |
| Автоповорот всего кадра по тексту | Повороты обрабатываются точечно в EasyOCR (`rotation_info`) для серийного номера |
| Определение типа прибора | Вне первой итерации |

## 6. Отладка

Если задан `DEBUG_SAVE_DIR`, для каждого запроса сохраняются промежуточные изображения с общим префиксом (идентификатор запроса): рабочая копия, результат CLAHE, маска бликов, найденный дисплей, варианты кропа с подписью распознанного текста. Это основной инструмент подбора параметров на датасете. В боевом режиме выключено, потому что изображения содержат чужие данные.

## 7. Производительность

Грубая оценка, подлежит замеру: этапы 1–4 порядка сотен миллисекунд на CPU при рабочей длинной стороне 1600 px. Основное время сервис тратит на EasyOCR (см. бюджет в [architecture.md](architecture.md#6-производительность-и-конкурентность)). Уменьшение `MAX_SIDE_PX` до 1280 ускоряет всё, но может хуже читать мелкий серийный номер, поэтому значение подбирается по метрикам.
