# REST-API CV-сервиса

Слой HTTP: `app/main.py` (маршруты, проверки входа, обработчики ошибок) и `app/schemas.py` (модели ответа). Бизнес-логики распознавания здесь нет, она за интерфейсом `OCREngine`.

В таблицах пометка **есть** означает, что поведение уже реализовано в заглушке, **новое** означает предложение.

## 1. Эндпоинты

| Метод и путь | Назначение | Статус |
|---|---|---|
| `POST /api/ocr` | Распознать показание на фото | есть |
| `GET /health` | Готовность сервиса | есть, расширяется |
| `GET /docs`, `GET /openapi.json` | Swagger UI и схема (из FastAPI) | есть |

Аутентификации нет, сервис доступен только из внутренней сети.

## 2. `POST /api/ocr`

**Запрос:** `multipart/form-data`, поле `file` (JPEG или PNG, до 10 МБ).

Проверки входа выполняются в таком порядке, на первой же ошибке возвращается ответ:

| № | Проверка | Ошибка | Статус |
|---|---|---|---|
| 1 | Есть поле `file` | валидация FastAPI | есть (`422`, формат `detail` списком) |
| 2 | `Content-Type` части `file` ∈ `image/jpeg`, `image/png` | `unsupported_media_type` | есть (`415`) |
| 3 | Чтение не больше `MAX_FILE_SIZE + 1` байт | — | есть |
| 4 | Файл не пустой | `empty_file` | есть (`400`) |
| 5 | Размер ≤ `MAX_FILE_SIZE` | `file_too_large` | есть (`413`) |
| 6 | Файл декодируется как изображение, число пикселей ≤ `MAX_IMAGE_PIXELS` | `invalid_image` | **новое** (`400`) |
| 7 | Найдены значение и серийный номер | `not_recognized` | **новое** (`422`) |

Проверка 2 опирается на заголовок части multipart, поэтому клиент обязан его выставлять. В C# для `ByteArrayContent` это нужно сделать явно (`Headers.ContentType`), иначе придёт `415`. Пример в README репозитория этого не делает, его стоит поправить. Рекомендуется дополнительно проверять сигнатуру содержимого, чтобы не зависеть от заголовка клиента.

## 3. Ответ `200`

```json
{
  "readings": [
    {
      "serial_number": "50794925145054",
      "reading_value": "50.99",
      "confidence": 0.88,
      "serial_confidence": 0.88,
      "value_confidence": 0.94,
      "bbox": { "x": 100, "y": 440, "width": 680, "height": 360 },
      "serial_bbox": { "x": 5, "y": 390, "width": 40, "height": 450 },
      "raw_text": null
    }
  ]
}
```

| Поле | Тип | Статус | Описание |
|---|---|---|---|
| `readings` | массив | есть | Один элемент. Массив оставлен для совместимости с заглушкой. Пустым **не бывает**: если ничего не найдено, возвращается ошибка `not_recognized` |
| `serial_number` | string | есть | Нормализованный серийный номер |
| `reading_value` | string | есть | Значение показания. Строка, ведущие и хвостовые нули сохраняются как распознаны, разделитель всегда точка |
| `confidence` | float 0..1 | есть | Общая уверенность: минимум из двух полей. Оставлена для обратной совместимости |
| `serial_confidence` | float 0..1 | **новое** | Уверенность по серийному номеру (ТЗ 5.3) |
| `value_confidence` | float 0..1 | **новое** | Уверенность по значению (ТЗ 5.3) |
| `bbox` | объект | есть | Область **значения** |
| `serial_bbox` | объект | **новое** | Область серийного номера |
| `raw_text` | string или null | **новое** | Весь распознанный текст для отладки (ТЗ 5.3, опционально). Заполняется только при `DEBUG_RETURN_RAW_TEXT=true`, иначе `null` |

Координаты `bbox` и `serial_bbox` заданы в пикселях **исходного изображения** с учётом EXIF-ориентации (то есть так, как фото видит пользователь), а не уменьшенной рабочей копии. Для повёрнутого вертикального серийного номера это обычный прямоугольник, охватывающий текст.

Все новые поля добавляются без удаления старых, поэтому клиент, не знающий о них, продолжит работать (при условии игнорирования неизвестных полей).

## 4. Ошибки

Тело ошибки для всех ошибок, которые формирует сервис (кроме валидации FastAPI):

```json
{
  "detail": {
    "code": "not_recognized",
    "message": "Не удалось распознать данные. Сфотографируйте счётчик так, чтобы в кадре были экран и серийный номер, без бликов.",
    "missing": ["serial_number"]
  }
}
```

| HTTP | `detail.code` | Когда | Статус |
|---|---|---|---|
| 400 | `empty_file` | Пустой файл | есть (сейчас `detail` строкой) |
| 400 | `invalid_image` | Файл не декодируется или слишком велик по пикселям | **новое** |
| 413 | `file_too_large` | Больше `MAX_FILE_SIZE_MB` | есть (строкой) |
| 415 | `unsupported_media_type` | Тип не JPEG/PNG | есть (строкой) |
| 422 | `not_recognized` | Не найдено значение и/или серийный номер. `missing` содержит список: `reading_value`, `serial_number` | **новое** |
| 422 | (нет `code`, `detail` списком) | Нет поля `file` (валидация FastAPI) | есть |
| 500 | `internal_error` | Непредвиденная ошибка. Подробности только в логе | **новое** (единый обработчик) |
| 503 | `not_ready` | Модели ещё загружаются (только `GET /health`, для `/api/ocr` по возможности) | **новое** |

Как отличить два вида `422`: у `not_recognized` поле `detail` объект с `code`, у ошибки валидации FastAPI `detail` список.

`not_recognized` это штатный ответ, а не сбой сервиса: логируется на уровне `INFO`. Остальные `4xx` для backend означают дефект его собственной проверки (кроме `invalid_image`).

Решение «любое ненайденное поле = ошибка» принято командой: пользователь должен переснять так, чтобы в кадр попали и экран, и серийный номер. Список `missing` позволяет приложению показать точную подсказку («не виден серийный номер» или «не виден экран») и при необходимости позже смягчить правило, не меняя формат ошибки.

## 5. `GET /health`

```json
{ "status": "ok", "mode": "real", "engine_ready": true }
```

| Поле | Описание |
|---|---|
| `status` | `ok` |
| `mode` | `mock` или `real` (есть) |
| `engine_ready` | **новое.** `true` после загрузки моделей и прогрева |

Пока `engine_ready=false`, ответ `503` с `detail.code = not_ready`. Backend использует этот эндпоинт как readiness-проверку.

## 6. Изменения контракта и влияние на backend

Клиент CV на стороне backend строился по контракту заглушки. Ниже изменения, которые нужно **согласовать с backend-командой** до внедрения:

| № | Изменение | Что должен учесть backend |
|---|---|---|
| 1 | Новые поля `serial_confidence`, `value_confidence`, `serial_bbox`, `raw_text` | Брать уверенность по полям, неизвестные поля не должны ломать разбор |
| 2 | Ошибка `422 not_recognized` вместо успеха с пустым списком | Не считать любой `4xx` дефектом интеграции: `422` с `detail.code = not_recognized` должен превращаться в понятную пользователю ошибку «не распознано», а не в `503`. Пустой `readings` больше не приходит, эту ветку оставить защитной |
| 3 | Ошибка `400 invalid_image` | Файл с корректным заголовком, но не декодируется: показывать пользователю как ошибку распознавания |
| 4 | Тело ошибок `detail: {code, message}` вместо строки | Разбирать по `code` |
| 5 | Значение показания: фиксированное число знаков после точки для модели (МИР С-04.10: 2), `reading_value` всегда в этом формате (`50.99`) | Принимать и хранить значение с таким числом знаков. Если backend рассчитан на другое число знаков, согласовать |
| 6 | Серийный номер: цифры, заглавные латинские буквы и дефис, 6–20 символов | Не ограничивать только цифрами, формат валидации согласовать |
| 7 | Ограничение числа одновременных запросов, `/health` отдаёт `503`, пока сервис прогревается | Readiness-проверка должна уметь `503`. Таймаут вызова 4 с оставить |

Нововведения вводятся только после согласования обеих сторон.

## 7. Заглушка и тестовые сценарии

Заглушка нужна backend и приложению для разработки, поэтому она должна уметь воспроизводить ошибки, а не только успех.

| Сценарий | Как включается (предложение) | Результат |
|---|---|---|
| `ok` | по умолчанию | `200`, данные как в образце: `50794925145054` и `50.99`, уверенность 0,85–0,99 |
| `low_confidence` | `?mock_scenario=low_confidence` | `200`, уверенность 0,3–0,6 |
| `not_recognized` | `?mock_scenario=not_recognized` | `422 not_recognized` |
| `invalid_image` | `?mock_scenario=invalid_image` | `400 invalid_image` |
| `slow` | `?mock_scenario=slow` | `200` после задержки 5 с (проверка таймаута backend) |

Параметр `mock_scenario` учитывается только при `USE_MOCK=true` и игнорируется в боевом режиме. Значения по умолчанию в заглушке стоит заменить на реалистичные (`serial_number` из цифр, `reading_value` с точкой), чтобы тесты backend проверяли правила формата, а не фиктивное `SN-00482913`.
